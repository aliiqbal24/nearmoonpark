# Persistent Moonpark

The current ruleset is moonpark-v9. New parks start with 3,200 credits, twice the v6 allocation. A 48×48 plot offers three times the original buildable area. Eight building types allow multiple copies. One human makes building decisions, while NPC visitors and two vendors run their own budgets and policies.

The first 12 rockets carry the same 96 paying guests for every opening score. Each guest has a finite wallet and visit. Their departure seals the score and its onchain proof hash. Construction, customization, income and visits continue after scoring. New regular guests bring game-issued test credits. Logistics shipments replenish goods under an explicit signed policy. These assets have no cash value.

New parks start with a connected Attention Kitchen, Finality Fizz and Dragonfly Garage. Their stock and working capital come from the initial fixed asset allocation. The player keeps the full 3,200-credit construction budget. Simulation time and the first rocket wait until the player draws and builds a coaster. The first meal introduces the food business's automatic stock purchases and 10% park share.

The coaster workshop places a station directly on the actual map. A player drags a route across tiles, closes the loop and adjusts ground-level handles and individual heights from 1.2 to 60 metres. The whole 48×48 map is available, with up to 256 route points. Collinear stroke samples are simplified. The station and a deterministic rail corridor reserve space, leaving irregular interiors available for other buildings. Paths can pass below elevated track. JavaScript and Rust share the same integer cubic occupancy calculation. Route occupancy is cached within each simulation instance and invalidated on construction, redesign and sale.

All attractions have appearance choices before construction. Lunar Bounce offers fixed 8, 14 and 22 metre heights, with distinct guest appeal. Track geometry and appearance are included in construction credits. Rides open automatically with fixed fares. Selling returns exactly half the invested construction credits, after existing passengers finish. Solar canopies earn five credits per twenty seconds from Logistics. Simulation runs at normal speed. Design workshops, dialogs and hidden tabs pause automatically. Paths preview a whole drag and purchase atomically on release.

The right-hand portraits expose each cameo's current status. Visitor thought bubbles derive from real needs, preference, queue and affordability state, with a small simultaneous limit and per-guest cooldown. The park foundation combines scanned regolith with small relief, crater washes, grading marks, mineral grit and subtle survey crosses. The larger passenger ferry retains the existing landing, boarding and departure cycle.

Published park revisions store their own canonical snapshots. A newer revision becomes public when its owner publishes it. The active park continues independently. A park retains its live run through sponsored operator rotation, including its token ledger and sealed score. Browser saves preserve the local operation journal. Private backups enable account recovery.

## NEAR architecture

`crates/moon-sim` is the shared deterministic Rust engine. It compiles to native code for tests and replays, browser WebAssembly for responsive prediction, and a dependency of `crates/moon-contract`. The contract build excludes the browser's raw WASM ABI. Build the browser and contract separately to avoid Cargo feature unification.

The client submits commands rather than claimed balances, states or scores. `create_run` admits a sponsored account; `apply_actions` validates ownership, revision, idempotent request ID, commands, costs and elapsed time. Batches have at most sixteen commands and twenty simulation ticks. A single path stroke contains deduplicated map cells, validates before spending and commits atomically. The contract limits simulation advancement to real elapsed time plus a small initial headroom, with no closing deadline. The first 96 visitors seal the score upon departure. A visit timeout and return shuttle ensure stranded visitors can leave. Later arrivals bring explicitly issued test credits, and the continuing park economy clears those mints, transfers and goods consumption atomically.

The browser predicts the continuing park economy locally, persists its operation journal and rebases on canonical contract responses. Only one transaction is submitted at a time. It uses finalized `EXECUTED` results, avoiding a wait for unrelated gas-refund receipts. A timed-out submission is read back and retried idempotently. Unconfirmed operations remain journaled through refresh and reconnect. A result stays pending until canonical confirmation.

The sponsor creates testnet subaccounts with a browser-generated recovery key and a restricted session key. The provisioning endpoint receives public keys. Verified Google sign-in optionally links the sponsored account through encrypted recovery storage. The session key can call `create_run`, `apply_actions` and `claim_prize`, has a finite allowance and cannot attach deposits. Initial funding is 0.5 testnet NEAR, with a 0.4 NEAR session allowance. Sponsorship has per-IP and global limits. The browser checks the remaining account balance and key allowance before a new round. Local browser storage holds the operation journal and signing keys. Authenticated account recovery stores only compact credentials, contract/run references and park identity, encrypted with AES-256-GCM and user/contract-bound authenticated data. The server holds the encryption key in a private environment secret. Restoring on another device fetches the canonical run from NEAR. Public exports exclude private keys. Offline practice stays browser-local.

The v9 contract is a keyless child account, separate from the sponsor. Onchain access-key queries return an empty list and the code exposes no upgrade method. Separate creator/prize liability counters prevent new run storage from consuming reserved backing. The sponsorship server checks storage headroom before admitting a new account. `fund_storage` retains only needed new sponsorship and refunds the remainder of that same deposit; it cannot withdraw old funds.

NPC businesses use separately keyed testnet accounts with a signed deterministic spending policy. The immutable contract executes that policy and maintains NEP-245 balances atomically with the game. Neon Postgres stores private profile, sponsorship and encrypted account-recovery records, with Neon managed Auth for sign-in. The NEAR contract stores canonical game outcomes, asset ownership and rankings. Details and custody boundaries are in `NEAR-ECONOMY.md`.
